# 分阶段对话与效果映射 (v0.6.8)

## 交互总则：基准需求优先与能力发现

修图的本质是**用户决定视觉效果与修改方向，代理负责技术参数、试片渲染与可复现交付**。
在 0.6.8 中，交互流程以**前置能力发现（capabilities）**为基石，以**基准需求多轮确认**为核心，以**持久化 Session 会话管理**为载体。

---

### 一、前置能力发现与参数沟通原则

1. **基于 Capabilities 提供可执行方向**：
   - 代理在向用户提建议前，先通过 `capabilities(detail=summary)` 获取当前运行环境与引擎的真实受控边界；需要参数时只取本轮类别的 full 定义（如支持白平衡、曲线、反差、饱和度、降噪、锐化、高光恢复、高光压缩、去马赛克、RAW 预处理、RAW 校准、镜头校正、输入色彩配置文件等 14 类受控参数）。
   - **只主动提供工具当前确实能执行的视觉方向**；对于不支持的能力（如人像局部磨皮提亮笔刷、路人/杂物 AI 消除、现成胶片滤镜预设等），绝不主动诱导或虚假承诺。
2. **默认免技术拷问与专业需求响应**：
   - 用户使用日常语言表达审美倾向时（如“希望整体通透些”、“想要傍晚暖暖的感觉”、“不要太刺眼”、“建筑边缘看起来有点弯”），**默认不用技术参数或滑块数值拷问用户，优先聚焦视觉效果与画面保持项**，不反向要求普通用户填写专业数值（如“请问您想要多少 K 色温？”、“您要几档 EV 曝光补偿？”、“曲线第一点坐标是多少？”、“您想用哪种去马赛克算法？”）。代理负责将用户的感知意图转化为合规参数范围内的试片配置。
   - **显式专业需求与歧义澄清**：若用户主动指定专业参数（如明确提出“色温定 5600K”、“压半档曝光”、“用 RCD 去马赛克”）、主动要求精确技术控制，或多项参数之间存在必须澄清的技术歧义时，允许并应当进行专业的技术确认与执行，**绝不能让低参数默认假设覆盖用户的显式专业要求**。

### 二、基准需求多轮确认铁律

处理照片前，代理必须围绕以下四大基准需求维度与用户达成共识：

1. **导出用途**：日常社交分享（默认 sRGB JPEG）、留存归档与继续精修（可加 16-bit TIFF）、画册打印/冲印（需明确尺寸、剪裁与色域规范）。
2. **核心主体与优先改善重点**：画面核心主体是谁或何物；当前最想解决的问题（如主体欠曝、背景杂乱、高光过曝发白、现场光偏色、暗部噪点明显、整体反差平淡、镜头畸变暗角等）。
3. **目标风格与调整强度**：期望的视觉氛围（自然真实、胶片复古、通透明快、浓郁电影感、日系清新等）；调整强度（微调克制、标准平衡、风格鲜明）。
4. **画面保留项与允许调整范围**：哪些特征必须严格保留（如现场暖灯氛围、人物真实肤色与毛发质感、特定景物固有色、暗部剪影意图等）；哪些部分允许大幅调整。

#### 暗部主体：把氛围词变成画面目标

看到主体偏暗、逆光大光比，或用户只给“聚光氛围/保留夜色/弱修图”等词而未说明可见度时，补问一个具体问题，例如：

> “这棵树希望看清树皮和主枝纹理，还是只要轮廓？可以选 A：主体清楚、环境仍暗；B：略提亮，保留若隐若现的细节；C：明确剪影。”

同时对齐“地面别抢戏”的具体含义：地面继续压暗、允许略亮，还是可接受背景高光稍亮以换取主体细节。只补缺失信息，不把每个暗场景都重问一轮。用户已选剪影、已明确主体需看清，或授权全权决定时，沿用其要求/已说明的假设；不能把“夜景”一词直接理解成剪影。

主体辨识度与氛围的优先级由用户决定。两者无法兼顾时，按用户已明确的取舍执行；未明确则展示差异并请用户选择，不自行把清晰、明亮或自然列为最高目标。剪影、朦胧、偏色或低调意图同样有效，不承诺看清所有细节。没有可查看画面或对应采样时，不从 ISO、单个像素值或整图均值猜测主体欠曝。

回述应具体到可观察结果，例如：“树干与主枝的纹理要能辨认；背景仍保留夜色；地面不要变成最亮的大块区域。”把它写入现有 confirmed_brief，并在 keep/change 保存用户确定的保持/修改项；不新增虚构请求字段。用户原话写 user_feedback，代理的推断不能冒充用户原话。换会话 load 后，先恢复这个目标再继续。

工具当前只有全局曝光/曲线等控制。如果主体与地面处于相同影调，全局提亮可能两者一起变亮。不能把 A 选项当已保证的局部提亮能力；若无法同时满足，说明“主体更清楚会连带提亮地面”的实看片段，按用户明确的优先级取舍；未明确时让用户选择全局折中或转入支持局部选区的软件。

#### 提问与确认规则：
- **已有信息绝不重复盘问**：从用户 prompt 和当前上下文读取已知信息，直接采纳，严禁反复盘问。
- **分轮针对性提问**：信息不完整时分轮提问，**每轮提出 2–3 个针对当前照片画面实际观察到的日常语言问题**，并提供清晰具体、结合画面的选项。
- **不设硬上限，不机械凑数**：根据照片复杂度自然提问，不机械凑数，默认不主动抛出专业数值题（用户主动提出时除外）。
- **关键需求缺失必须等待**：关键需求缺失时，必须向用户提问并**等待用户明确回复**；严禁因模型等待、超时或臆测默认值而擅自代答。
- **首次出图前回述确认**：在正式调用工具生成第一张试片前，必须将整理出的基准需求（用途、主体可见度、目标风格、保留项）用简明语言回述给用户并请求确认；已有明确授权确认时不重复回述。
- **全权委托快捷路径**：**仅当**用户在指令中明确表示“你全权决定”、“直接出图”、“按你觉得最好的直接来”时，代理方可走快捷路径。走快捷路径时，必须明确向用户声明所依据的基准假设，然后直接开始渲染。

### 三、先建立感知基线，再拆解风格

“微调克制”须结合用户的具体限制理解；若用户未限制明暗变化幅度，不机械限制达到已确认可见度所需的调整量。不要为了维持微小曝光值而交付看不清主体的图，也不要为了显得做了风格而多加无关参数。

- 按 [raw-workflow.md 的感知基线与门禁](raw-workflow.md#感知基线与可见度复查门禁) 检查起片：先让主体达到已确认的可见度，再判断冷暖、反差、饱和度和氛围。首片已经满足基线时，可同时完成风格，不为形式多渲染一次。
- 只要求自然校正、提亮或改善可见度时，合适的曝光/曲线调整可以就是完整答案；需要风格化时，不能仅提亮就宣称已完成“胶片/电影感”。
- 把风格词拆成可检查变化，避免固定配方：“日系清新”先确认主体清楚程度与是否接受较柔反差/偏淡色彩；“复古暖调”确认哪些暖色要保留、哪些偏黄要纠正；“聚光氛围”确认主体纹理与环境明暗关系。方向依实际画面与工具能力选择，不预填统一 EV、色温或抬黑点。
- 色温、曝光、全局曲线与反差的变化会互相影响观感，每轮回看主体、高光与背景，不以“参数都成功执行”代替视觉验证。风格变化不能悄悄破坏已确认的可见度和 Keep。
- 交付描述必须对应实际打开的试片，例如“树皮比上一版清楚，地面也略亮”；未看见或未验证的变化不写成“层次保留完美、细节纯净”。无法看图时，说明仍待用户视觉判断，只提供诊断试片，不能称已完成审美验收。

### 四、默认 Session 流程与跨会话恢复

**所有实际修图任务必须默认建立并使用 Session 容器。旧的无状态 render 仅作为向后兼容保留，不再是 Skill 的默认行为。**

1. **项目开始**：
   - 确认基准需求后，立即调用 `session` 的 `init` 操作，在用户项目目录下创建 `session.json`。
   - 记录 `source`、`base_profile`（及其 SHA-256）、`confirmed_brief` 及初始 `keep`/`change`。
   - **支持初始参数**：可在 `init` 时直接注入初始 `adjustments`（及 `exposure_ev`），版本保持 `revision: 0`，`history: []`；校验失败立即安全闭合。
2. **每轮反馈沉淀**：
   - 用户提出反馈时，先按下文意图维护规则整理仍有效的目标与保持项，再调用 `session` 的 `record_feedback` 记录原话及更新项，归档上轮快照，推进 `revision`。
3. **Render Gate 门禁、绑定渲染与 CAS 审计保护**：
   - 调用 `render` 时传入 `session_path` 与当前 `expected_revision`。
   - 工具首先申请该 session 的独立门禁锁（`.render.gate`）。若同一会话已有其他渲染在执行，工具立即返回 `RENDER_IN_PROGRESS`。**向导严禁盲目发起重试轮询循环**，应告知用户该照片正在生成试片；
   - 门禁不锁会话数据，用户可在渲染期间随时查看状态或追加反馈；
   - 渲染引擎先在短锁下读取快照，随后在锁外进行耗时 RT 渲染与 QC；最后短锁核验 CAS 版本与 Session 身份再行提交；
   - **晚反馈冲突处置**：若渲染耗时期间用户已追加新反馈（导致 revision 递增冲突），CAS 提交中止并返回 `REVISION_CONFLICT`。生成的试片保留为可审计孤立产物（携带 manifest），**绝对不会覆盖用户最新反馈**。向导应重新调用 `session load` 检查最新记录并由用户当前目标决定是否重新调参渲染。
4. **交付时展示可点存档路径（跨会话无缝恢复）**：
   - 每次试片交付或最终交付时，在回答中明确附上 Markdown 可点击链接展示该 session 文件的绝对路径（链接目标须取自工具返回的实际 session_path，不使用虚构示例路径）。
   - **用户换了聊天窗口时的恢复方式**：告知用户若开启新对话，只需将此路径发给向导（“继续修这张，session 路径是...”），向导通过 `session load` 即可瞬间恢复完整上下文、累积有效参数、基准需求与 Keep/Change 历史，**避免让向导在全磁盘盲搜**。

### 五、增量参数继承、单项复位（reset_fields）与用户文本定位

1. **增量继承与完整校验（白平衡示例）**：
   - 增量请求支持仅提供需修改的子字段（例如第 1 轮为 `temperature: 5800, green: 1.05`，第 2 轮用户希望偏冷一点，增量仅提交 `temperature: 5200`）。
   - 系统先校验 patch 合法性（类型/范围/已知键），再与会话累积参数深度合并，最后执行全量有效性校验。因此 `green: 1.05` 会被自动继承保留，不会被误拒绝。
   - **无历史或复位时的完整性要求**：在初次无历史渲染或显式 `reset_adjustments: true` 时，白平衡必须成对提供完整字段；若缺少任一字段将被严格拒绝，禁止默认乱填。
2. **单项受控复位（`reset_fields`）机制**：
   - 支持白名单 14 类类别受控复位：`['exposure_ev', 'contrast', 'saturation', 'white_balance', 'tone_curve', 'denoise', 'sharpen', 'highlight_recovery', 'highlight_compression', 'demosaic', 'raw_preprocess', 'raw_calibration', 'lens_correction', 'input_profile']`。
   - 语义：继承历史 ➔ 移除指定字段 ➔ 合并新 patch ➔ 完整校验。
   - **白平衡复位语义**：复位白平衡是将白平衡调整移除出有效参数，使 RawTherapee 回归应用 Base PP3 模板的预设白平衡。**这绝不等于恢复相机拍摄时的原始白平衡**。若复位后重新提供白平衡 patch，必须成对提供完整字段，否则严格拒绝。
   - **模式切换语义**：切换 `lens_correction` 或 `input_profile` 模式时，必须传入 `reset_fields` 清除旧字段。
   - **互斥规则**：`reset_fields` 与 `reset_adjustments` 互斥，禁止同时传入。
3. **意图维护：全量替换前先整理仍有效的目标**：
   - `keep` / `change` 传入即全量替换；先 load，新增保持项须与仍有效的旧项合并。例如已有“保留暖光”，用户说“反差也保留”，提交两项而非仅新项。未变化的列表省略；仅在用户明确撤销或改变目标时移除对应保持项。
   - `change` 表示当前待办，不无限追加旧要求。已完成且用户认可的项目移出待办；尚未确认完成的项目不擅自当作满意项。没有待办时可明确提交空列表，不能因此清空 Keep。
   - 用户改变风格、可见度或取舍时，同步修订 `confirmed_brief` 和受影响的 Keep/Change，避免新反馈与旧目标并存。例如“改成剪影”须撤销原先“树皮纹理清楚”的相冲突目标；矛盾尚未明确解决时只问该冲突。
   - `user_feedback` 保存用户原话；代理对目标的整理放在 confirmed_brief / keep / change，不能把推断、技术记录或推荐写成用户说过的话。
4. **参数深合并与显式复位**：
   - 绑定渲染默认将新参数与前序累积参数进行字典深合并；
   - 用户要求“推倒全部重来”时，指定 `reset_adjustments: true`；要求“仅白平衡或曲线重来”时，指定 `reset_fields: ['white_balance']`。
5. **用户原话的定位（诚实声明）**：
   - 用户在 `keep` 中记录的文字（如“保留现场夕阳暖光感”），系统完整保存在 session 快照与 manifest 中作为人机审计凭据；
   - **系统不承诺存在神秘的“自然语言自动物理约束器”**；保持效果依赖代理在调整其他参数时的人工语义复核与小步验证，并在交付时主动提示用户重点核对。

### 六、选版、继续编辑与审美验收

- **执行复查与审美认可分开**：代理检查文件可用、参数执行和画面是否符合已确认要求，描述观察到的差异与代价；最终喜欢哪版、接受哪些代价由用户决定。每次反馈聚焦本轮实际变化，不要求用户重新填写全部需求。
- **对照有明确基准**：展示用户已选版与本轮候选，用中性描述如“树干更亮、地面也更亮”；避免把选项命名为“专业版/正确版/失败版”来诱导选择。不必每轮出多张；存在难以用文字决定的取舍时提供少量对照。
- **选中版持久化**：用户选定后，通过 record_feedback 将其原话记录在 user_feedback，并在 confirmed_brief 保留当前目标、用户选中或定稿的真实 output / manifest 绝对路径；后续改写需求摘要时继续保留选版信息，除非用户更换选择；先由 Session history 核对归属与文件存在性。不能只写“第二张”或把 Session revision 当成照片编号。没有明确选版时记为待选择；推荐不等于用户确认。
- **回到旧版继续**：选择旧版本身不改变 effective_adjustments。用户要求从旧版继续时，核对该版 manifest 与历史记录的绑定/哈希，取其完整 effective_adjustments；用现有 record_feedback 的 reset_adjustments=true 配合该完整参数快照恢复，再做本轮修改，避免最新探索版的额外参数残留。沿用当前源与 Base 锚点，不复制旧 revision；导出选项从所选版 history.export 显式复用。资源缺失或图片已精简时说明事实，不伪称已恢复或已查看。
- **停止与定稿**：连续两次同方向试片无可见收益时停止盲目试参，呈现候选和限制。保留用户已选版；没有选版时可给出推荐理由并等待选择，不自行宣布“最佳版”。用户明确委托代选/定稿时按其范围执行，记录为“按用户授权由代理选定”，不伪造用户满意反馈；用户提出新方向后可继续。
- **清理保护选中版**：无论它是否最新，都不要将当前用户选中/定稿版加入 prune_history 名单。工具自动保护的是最新成功成片，不解析 confirmed_brief 里的偏好；旧选中版的保护由代理在清理预览时落实。

### 七、孤立产物清理（Clean）交互准则

1. **必须明确用户清理意图**：
   - `clean` 操作支持单会话 `session_path` 或多会话 `session_paths`（元素唯一）。默认仅做安全扫描预览（`apply: false`），展示孤立候选与可释放字节数。
   - 仅当用户明确指示“清理未采用的中间试片 / 清理磁盘缓存”时，方可执行 `apply: true` 物理删除。**绝不在后台静默自动执行 GC**。
2. **清理范围限制与保守安全保护边界**：
   - **Clean 仅清理未提交孤立试片，绝不支持且不能实现“删除历史仅留最终”**。所有在 session history 中成功备案的成片目录受永久保护。
   - 默认保留时间阈值为 `min_age_seconds: 1800`（30 分钟），严防误删近期操作。
   - 仅允许清理带有合法 `cleanup_protocol_version: 1` 或已知 0.4.1 manifest 且确证归属于指定 session、但未在 session 历史备案的孤立目录。
   - 所有指定 session 执行删除前新鲜读取（校验身份与 schema），遭遇损坏或被替换的 session 时严格失败闭合，保证零误删。
   - 正在渲染中的活动目录（持有 `.active.lock`）、已提交至历史的成片、其他 session 的产物、旧版或未知协议目录一律保守跳过保护。

### 八、工具能力与边界规范（诚实表达）

| 需求场景 | 真实技术动作 | 边界与标准回复 |
|---|---|---|
| “人像面部提亮 / 磨皮美颜” | 全局曲线微调暗部与中灰，控制中性灰白平衡 | 明确告知工具仅支持全图光学影调调整，无局部面部笔刷/磨皮选区。建议定稿后在外部修图软件做局部精修。 |
| “把右下角路人 / 杂物擦掉” | 不执行消除，可提供二次构图与裁切建议 | 明确说明本工具为光学 RAW/JPEG 显影引擎，无生成式 AI 填补/消除功能。 |
| “直接套个富士经典底片预设” | 拆解为色温、曲线压缩与反差调整试片 | 说明无开箱即用的黑盒胶片预设，通过自定义白平衡与 S 曲线渲染一组胶片影调试片供评测。 |
| “再亮一点 / 暗部太死” | 小步调整 `exposure_ev` 或 `tone_curve` | 检查高光过曝剪切，JPEG 源警惕色阶断层。 |
| “更暖一点 / 更冷一点” | 调整 `white_balance`（temperature + green） | 说明 JPEG 参数为 RawTherapee 对已烘焙图像的颜色调整控制，相对当前试片调整冷暖与偏色，需预览确认，数值不代表重新设定拍摄白平衡，5500 不保证中性；RAW 有更多白平衡调整信息也不自动保证精准校色。 |
| “反差太大 / 太刺眼” | 降低 `contrast`，或应用柔和色调曲线与 `highlight_compression` | 检查画面是否发灰缺乏立体感。 |
| “高光过曝发白，还有没有细节？” | RAW 源启用 `highlight_recovery` 配合 `highlight_compression`；必要时调用 `raw_qc` 检查 CFA 溢出 | 明确说明 RAW 可利用未过曝通道重建高光色彩；若为 JPEG 则说明纯白 (255,255,255) 物理硬剪切限制，仅能滚降高光曲线防止刺眼。 |
| “广角拍的建筑边缘歪了 / 四周有暗角” | 对 RAW 源配置 `lens_correction`（如 `mode: lensfun_auto` 或 `lcp`） | 说明为全局光学模型校正，需有匹配的镜头数据库或 LCP 文件。 |
| “换一个镜头配置文件或色彩查找表” | 使用 `reset_fields: ['lens_correction']` 或 `reset_fields: ['input_profile']` | 清除旧模式或损坏路径字段，安全重新绑定新配置。 |
| “查一下这张 RAW 原片传感器有没有彻底过曝” | 调用 `raw_qc` 返回未旋转可见 CFA 码值统计与溢出比例 | 向用户客观解释原始数字码值与饱和溢出情况；说明此数据仅供技术评估，不自动套用为黑白点偏移或常规曝光。 |
| “更干净 / 噪点少一点” | 调整 `denoise`（luma / chroma），NEF 可启用 `raw_preprocess.line_noise` | 100% 放大检查边缘毛发，防过度涂抹产生塑料蜡感。 |
| “白平衡调乱了，仅复位白平衡但保留曲线和曝光” | 指定 `reset_fields: ['white_balance']` | 清除累积白平衡，恢复 Base PP3 模板预设白平衡（注意非相机白平衡），保留其他有效调整。 |
| “回退到最开始的参数” | 指定 `reset_adjustments: true` | 清除全部累积参数，回归 base profile 纯净起点。 |
| “帮我把没用的中间试片删掉” | 按范围用 clean / prune_history，先预览 | 先区分孤立试片与已提交历史：前者用 clean，后者按 export-and-retention.md 用 prune_history。预览名单符合已有清理授权才 apply；保护用户选中版，不重复索取已有授权。 |
